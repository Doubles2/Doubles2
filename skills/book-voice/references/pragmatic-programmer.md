# 실용주의 프로그래머 목소리

『실용주의 프로그래머』 20주년 기념판(데이비드 토머스·앤드류 헌트, 인사이트)을
사용자가 1~2장(Topic 1~12) 원본 사진으로 읽으며 관찰한 특징이다.

**한 줄 요약**: 경험 많은 선배 둘이 "우리"로서 "여러분"에게, 일화와 비유로 웃기면서 한 가지 원칙을 단단히 박아 넣는 짧은 에세이.

## 구성 틀 (Topic 하나)

1. **여는 인용**: 주제와 비스듬히 닿는 명언 한 줄 + 출처. (예: 철학자·배우·영화 대사·"미상")
2. **장면으로 시작**: 독자가 겪어 봤을 법한 상황이나 짧은 일화로 문제를 꺼낸다.
   기억에 남는 이미지 하나를 만든다(깨진 창문, 돌멩이 수프, 삶은 개구리, 예광탄, 헬리콥터 조종).
3. **문제 → 원리**: 왜 그런 일이 생기는지 한두 문단으로 설명하고, 소프트웨어 상황으로 옮긴다.
4. **Tip 박스**: 번호 붙은 명령형 한 문장. 짧고 기억하기 쉽게. ("~하라", "~하지 말라", "~이란 없다")
5. **소제목 몇 개로 넓히기**: 적용 방법, 예외, 흔한 오해. 소제목도 짧은 명령형이나 명사구.
6. **대비로 선 긋기**: 비슷한 개념과의 차이를 따로 강조한다("이 둘의 차이점은 정말 중요하기 때문에 재차 강조하겠다" 같은 방식).
7. **관련 항목**: 다른 Topic 번호와 제목 목록.
8. **도전해 볼 것 / 연습 문제**: 독자에게 던지는 열린 질문 2~3개. 자기 프로젝트에 적용해 보게 한다.

## 문장 습관

- 저자는 **"우리"**, 독자는 **"여러분"**. 경험담은 "우리는 ~한 적이 있다", "우리가 보기에는".
- **짧은 단정문**으로 끊어 친다: "이게 전부다.", "영원한 것은 없다.", "못 한다."
- **수사 의문문**으로 독자를 찌른다: "왜 직접 바꾸지 않습니까?", "상자를 열 용기가 있는가?"
- **유머와 과장**: 진지한 원칙 옆에 엉뚱한 농담 한 줄(고양이 탓, 고무 오리, "헬리콥터 조종사라면 생선을 먹지 말라").
- **비유를 끝까지 끌고 간다**: 예광탄 비유를 꺼냈으면 조준·발사·궤적까지 그 비유 안에서 설명한다.
- **반대 입장을 먼저 인정하고 뒤집는다**: "~라고 생각하는 사람도 있을 것이다. 그러나 다른 점이 있다."
- 원칙을 여러 사례에 반복 적용해 **후렴**처럼 만든다: "왜 결합도를 줄이면 좋은가? … ETC. 왜 이름 짓기가 중요한가? … ETC!"
- 책 안에서 서로 참조한다: "(○○쪽의 〈항목 N. 제목〉 참고)".

## 직접 쓴 짧은 예문 (이 목소리의 느낌)

> **데이터는 늘 더럽다**
>
> 깨끗한 데이터는 교과서에만 있다. 여러분이 받은 CSV에도 어딘가 빈 칸이 있고, 날짜는 세 가지 형식으로 섞여 있으며, 누군가 "N/A"를 문자열로 적어 두었을 것이다.
>
> 우리는 모델이 이상하게 동작할 때마다 먼저 모델을 의심하는 사람들을 많이 봤다. 하이퍼파라미터를 바꾸고, 층을 쌓고, 밤을 샌다. 그런데 범인은 대개 데이터 세 번째 줄에 있다.
>
> **Tip. 모델을 고치기 전에 데이터를 의심하라.**
>
> 그러니 학습 버튼을 누르기 전에 데이터를 열어 보라. 직접, 눈으로. 행 몇 개를 출력하는 데는 1분이면 충분하다. 그 1분이 여러분의 주말을 지켜 줄 것이다.

## 글 끝 정리 형식

```
관련 항목
- (관련 주제 2~4개)

도전해 볼 것
- (독자가 자기 일에 적용해 볼 질문 2~3개)
```
