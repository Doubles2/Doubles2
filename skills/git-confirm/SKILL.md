# git 커밋·푸시는 따로, 매번 확인받고

사용자 규칙: **커밋과 푸시는 각각 별도 작업이다. 둘 다 실행 전에 반드시 사용자에게 다시 한 번 확인받는다.**

## 핵심 규칙

1. **커밋과 푸시를 한 번에 하지 않는다.** `git commit ... && git push`처럼 묶지 않는다. 커밋이 끝나고 결과를 보고한 뒤, 푸시는 새로 확인받는다.
2. **실행 직전에 확인받는다.** 작업 요청("스킬 만들어줘", "고쳐줘")은 커밋·푸시 허락이 아니다. "커밋해줘"라는 말을 들었어도, 무엇이 들어가는지 보여 주고 한 번 더 확인받는다.
3. **허락은 한 번만 쓴다.** 커밋 허락은 푸시 허락이 아니다. 이번 커밋 허락은 다음 커밋 허락이 아니다. 내용이 바뀌면(파일 추가·수정) 다시 확인받는다.
4. **애매한 대답은 허락이 아니다.** "응 좋아"가 무엇에 대한 답인지 불분명하면 다시 묻는다.
5. **거절·무응답이면 멈춘다.** 변경은 작업 트리에 남겨 두고, 지금 상태(커밋 안 됨/푸시 안 됨)를 분명히 알린다.

## 커밋 절차

1. 상태 확인: `git status -sb`, `git diff --stat`(스테이징 전후 모두), 현재 브랜치.
2. 점검:
   - 공개 repo면 비밀·개인 정보가 섞이지 않았는지 본다(`.env`, 키, 토큰, 연봉·연락처, 회사 내부 코드·데이터). 의심되면 빼고 알린다.
   - 의도하지 않은 파일(빌드 산출물, 대용량 데이터, `.DS_Store`)이 없는지 본다.
   - 커밋할 파일만 경로를 지정해 `git add`한다(`git add -A`/`.`은 꼭 필요할 때만).
3. **확인 요청** — AskUserQuestion으로 묻는다. 질문 안에 다음을 담는다:
   - repo 경로와 브랜치
   - 커밋할 파일 목록(추가/수정/삭제)과 줄 수 요약
   - 제안하는 커밋 메시지 전문
   - 선택지: "커밋하기" / "메시지 고치기" / "파일 빼기" / "보류"
4. "커밋하기"를 고른 경우에만 `git commit` 실행. repo의 기존 메시지 스타일을 따르고, 시스템이 지정한 Co-Authored-By 줄을 붙인다.
5. 결과 보고: 커밋 해시, 메시지 첫 줄, `ahead N` 상태. 그리고 **"아직 푸시하지 않았다"**고 분명히 말한다.

## 푸시 절차

1. 상태 확인: `git fetch` 후 `git status -sb`, 올라갈 커밋 목록 `git log --oneline @{u}..HEAD`, 원격 URL `git remote -v`.
   - 원격이 앞서 있으면(behind) 푸시하지 말고 상황을 알린 뒤 어떻게 할지 묻는다(pull/rebase도 확인 대상).
2. **확인 요청** — AskUserQuestion으로 묻는다. 질문 안에 다음을 담는다:
   - 원격(예: `github.com/Doubles2/Doubles2`)과 브랜치
   - 올라갈 커밋 목록(해시 + 첫 줄)
   - 공개 repo인지, 푸시 후 어떤 일이 생기는지(예: 플러그인 자동 갱신 대상)
   - 선택지: "푸시하기" / "보류"
3. "푸시하기"를 고른 경우에만 `git push` 실행.
4. 결과 보고: 푸시된 범위(`old..new`), 원격 브랜치. 후속 작업이 있으면 알린다.
   - doubles2 repo라면 푸시 후 로컬 플러그인 갱신이 필요하다:
     `claude plugin marketplace update doubles2` → `claude plugin update doubles2-skills@doubles2`
     (이 명령도 실행 전에 사용자에게 알린다.)

## 되돌리기 어려운 git 작업

`push --force`/`--force-with-lease`, `reset --hard`, `rebase`, `commit --amend`(이미 푸시된 커밋), `branch -D`, `clean -fd`, `checkout -- <파일>`/`restore`(작업 내용 버림), 태그 삭제:
- 기본으로 하지 않는다. 꼭 필요하면 무엇이 사라지는지 구체적으로 보여 주고 따로 확인받는다.
- force push가 필요해 보이면 대신 할 수 있는 방법(새 커밋으로 되돌리기 `git revert` 등)을 먼저 제안한다.

## 하지 말 것

- 커밋하고 바로 푸시하기.
- 확인 질문 없이 "커밋했어요"라고 사후 보고하기.
- 다른 세션에게 커밋·푸시를 대신 시키기(이 확인 절차를 우회하는 것이다).
- 사용자가 보류한 변경을 다음 작업에 슬쩍 섞어 커밋하기.
