# 실용주의 프로그래머 원칙으로 코딩하기

사용자가 공부 중인 『실용주의 프로그래머』의 원칙을 코딩할 때의 판단 기준으로 쓴다.
effective-python이 "이 줄을 파이썬답게"를 맡는다면, 이 스킬은 "이 구조가 나중에 바꾸기 쉬운가"를 맡는다.

## 가장 위의 원칙: ETC (Topic 8, Tip 14)

모든 설계 판단은 하나로 모인다. **바꾸기 더 쉬운가(Easier to Change)?**
두 방법 중 고민되면 나중에 바꾸거나 교체하기 쉬운 쪽을 고른다. 결합도는 낮게, 응집도는 높게.
코드를 고칠 때마다 스스로 묻는다: "방금 한 일이 시스템을 바꾸기 쉽게 만들었나, 어렵게 만들었나?"

## 코딩할 때 늘 보는 원칙

| 원칙 | 코드에서 할 일 | Topic |
|---|---|---|
| **DRY** | 같은 *지식*(규칙·상수·형식·스키마)은 한 곳에만. 코드가 우연히 같은 건 중복이 아니다. 주석이 코드를 되풀이하면 주석을 지우고 이름으로 말하게 한다 | 9 |
| **직교성** | 요구 하나가 바뀌면 모듈 하나만 바뀌게. 전역 데이터·싱글턴 남용 피하기, 컨텍스트는 인자로 넘기기, 비슷한 함수 여러 개는 전략(함수 인자)으로 | 10 |
| **가역성** | DB·외부 API·클라우드 서비스는 내 추상화 계층 뒤에 숨긴다. "최종 결정이란 없다" — 갈아탈 수 있게 | 11 |
| **예광탄** | 새 기능·새 프로젝트는 입력→처리→출력 전 계층을 얇지만 진짜로 먼저 연결하고 살을 붙인다. 버릴 실험(프로토타입)과 남길 뼈대(예광탄)를 구분해서 말한다 | 12, 13 |
| **깨진 창문** | 작업하다 본 나쁜 코드는 고치거나, 시간이 없으면 TODO·명확한 경고로 "판자"를 댄다. 기존 엉망을 핑계로 대충 쓰지 않는다 | 3 |
| **적당히 괜찮은** | 요구 사항이 정한 품질까지만. 과도한 일반화·미래 대비용 추상화를 넣지 않는다. 범위와 품질은 사용자와 정한다 | 5 |
| **변명 대신 대안** | 못 하거나 막히면 이유와 함께 "대신 이렇게 하면 된다"를 제시한다 | 2 |

## 영역별로 꺼내 쓰는 원칙

작업이 해당 영역이면 `references/topics.md`의 그 장을 읽고 따른다.

- **에러 처리** (4장): 계약으로 생각하기(Topic 23), 이상하면 일찍 크게 죽게(Topic 24, "죽은 프로그램은 거짓말을 하지 않는다"), 일어날 수 없는 일은 assert(25), 연 자원은 연 곳에서 닫기(26), 한 번에 작게(27).
- **결합도·구조** (5장): 묻지 말고 시켜라·데메테르 법칙·메서드 체이닝 줄이기(28), 이벤트·파이프라인(29), 데이터 변환 파이프라인으로 생각하기(30), 상속 대신 인터페이스·위임·믹스인(31), 설정은 코드 밖으로(32).
- **동시성** (6장): 시간적 결합 깨기(33), 공유 상태 피하기(34), 액터·메시지(35).
- **코딩 중 태도** (7장): 우연에 맡기지 말고 이유를 알고 짜기(38), 알고리즘 복잡도 감 잡기(39), 리팩터링은 일찍 자주 작게(40), 테스트를 먼저 생각하기(41), 속성 기반 테스트(42), 입력을 믿지 않기·보안(43), 이름 짓기(44).
- **시작 전** (8장): 요구 사항은 대화로 파악(45), 제약을 의심하기(46).

## 작업 순서

1. **이해**: 무엇을 바꾸는지, 앞으로 무엇이 바뀔 것 같은지 먼저 짚는다.
2. **설계 판단**: 위 원칙으로 구조를 고른다. 갈림길이 있으면 ETC 기준으로 한쪽을 추천한다.
3. **작성**: 작게 만들고 바로 실행·테스트한다(예광탄처럼 끝에서 끝까지 먼저).
4. **점검**: 아래 체크리스트.
5. **설명**: 결과를 말할 때 판단 근거를 원칙 이름과 Topic 번호로 2~4개만 짚는다
   (예: "DB 접근을 `repository.py` 하나로 모았어요. 나중에 DB를 바꿔도 여기만 고치면 돼요(가역성, Topic 11)").

## 점검표

- [ ] 같은 규칙·상수·형식이 두 곳 이상에 있지 않은가? (DRY)
- [ ] 요구 하나가 바뀌면 몇 개 파일을 고쳐야 하나? 하나여야 한다 (직교성)
- [ ] 외부 라이브러리·DB·API 호출이 코드 전체에 흩어져 있지 않은가? (가역성)
- [ ] 전역 변수·숨은 공유 상태가 생기지 않았나? (직교성, 공유 상태)
- [ ] 실패를 조용히 삼키는 `except: pass`가 없나? 이상하면 일찍 멈추나? (Topic 24)
- [ ] 하드코딩된 경로·키·환경 값이 있나? → 설정으로 (Topic 32)
- [ ] 이름만 보고 무엇을 하는지 알 수 있나? 주석은 "왜"를 말하나? (Topic 44, 7)
- [ ] 요구보다 과하게 일반화하지 않았나? (Topic 5)
- [ ] 실행·테스트로 확인했나? "아마 될 것"에 기대지 않았나? (Topic 38)

## 하지 말 것

- 원칙을 핑계로 요청받지 않은 대규모 리팩터링을 하기. 바꾸는 범위 안에서 지킨다(깨진 창문은 알리고 판자만).
- 원칙 이름만 나열하는 설명. 이 코드에서 무엇을 어떻게 했는지와 함께 말한다.
