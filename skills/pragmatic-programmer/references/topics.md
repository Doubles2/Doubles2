# 53개 Topic 코딩 적용 요령

✅ = 사용자가 원본 사진으로 읽고 노션에 정리한 Topic(그 Topic의 Tip 번호를 함께 적음).
화살표 뒤는 코딩할 때 실제로 할 일이다(직접 풀어 쓴 요약, 책 문장이 아님).
아직 공부하지 않은 Topic은 책의 큰 뜻만 적었다. 사용자가 정리하면 Tip 번호와 함께 보강한다.

## 1장 실용주의 철학

1. ✅ 당신의 인생이다 (Tip 3) → 환경이 불만이면 바꾸거나 떠난다. 코딩에선: 불편한 도구·절차를 참지 말고 개선을 제안한다.
2. ✅ 고양이가 내 소스 코드를 삼켰어요 (Tip 4) → 막히면 변명 대신 대안. 백업·버전 관리 없이 작업하지 않는다. 모르면 "알아보겠다".
3. ✅ 소프트웨어 엔트로피 (Tip 5) → 깨진 창문(나쁜 설계·코드)을 방치하지 않는다. 당장 못 고치면 주석 처리·미구현 표시·더미로 판자를 댄다.
4. ✅ 돌멩이 수프와 삶은 개구리 (Tip 6, 7) → 큰 변화는 작게 동작하는 것부터 보여 주고 키운다. 작은 품질 저하가 쌓이는지 늘 주변을 본다.
5. ✅ 적당히 괜찮은 소프트웨어 (Tip 8) → 품질 수준을 요구 사항으로 정한다. 완벽주의로 덧칠하지 않고 멈출 때를 안다.
6. ✅ 지식 포트폴리오 (Tip 9, 10) → 새 기술은 작게라도 꾸준히. 라이브러리·블로그 주장은 비판적으로 검증한다.
7. ✅ 소통하라! (Tip 11–13) → 문서는 코드와 함께, 주석은 "왜"를, 독자에 맞춰 쓴다.

## 2장 실용주의 접근법

8. ✅ 좋은 설계의 핵심 (Tip 14) → ETC. 모든 설계 원칙은 바꾸기 쉽게 하려는 것. 모르면 교체하기 쉬운 쪽.
9. ✅ DRY: 중복의 해악 (Tip 15, 16) → 지식은 한 곳에. 코드·주석·스키마·API 명세·사람 사이 중복까지. 단, 우연히 같은 코드는 중복이 아니다. 계산 가능한 값은 저장하지 말고 계산(필요하면 캐시를 클래스 안에 숨김).
10. ✅ 직교성 (Tip 17) → 관련 없는 것끼리 영향이 없게. 계층 구조, 부끄럼쟁이 코드, 전역·싱글턴 피하기, 외부 식별자(전화번호 등)에 의존하지 않기.
11. ✅ 가역성 (Tip 18, 19) → 최종 결정은 없다. 외부 API·DB는 추상화 뒤로, 코드는 컴포넌트로. 유행을 좇지 않는다.
12. ✅ 예광탄 (Tip 20) → 전 계층을 얇게 끝까지 연결한 진짜 코드부터. 남기는 코드라 오류 검사·구조·테스트를 갖춘다.
13. ✅ 프로토타입과 포스트잇 (Tip 21) → 위험한 부분(새 아키텍처·외부 데이터·외부 라이브러리·성능·UI) 하나에 답하려는 버릴 실험. 정확성·완전성·안정성·스타일은 무시해도 되고, 코드가 아니어도 된다(포스트잇·화이트보드). 시작 전에 "버릴 코드"라고 밝히고, 교훈만 기록해 가져간다. 아키텍처를 볼 땐 "각 모듈이 필요한 데이터에 필요한 시점에 닿는가"를 꼭 확인. 세부를 포기할 수 없거나 오해받기 쉬우면 예광탄으로. 노트북 실험 코드를 그대로 제품(배치·서비스)으로 옮기지 않는다.
14. ✅ 도메인 언어 (Tip 22) → 문제 도메인에 가깝게 프로그래밍한다. 이름·함수를 도메인 어휘로 짓는 것이 기본이고, 필요하면 도메인 언어까지. 단 언어를 만드는 비용이 절약보다 커지면 안 된다. 고르는 순서: ① YAML·JSON·CSV처럼 널리 통용되는 외부 형식(설정·명세) ② 내부 언어(호스트 언어 위의 API — 호스트 기능을 공짜로 쓰지만 문법은 못 벗어남) ③ 메타프로그래밍 대신 그냥 도메인 이름의 함수. 직접 파서를 만드는 외부 언어는 사용자가 직접 그 언어로 쓰는 경우에만. 요구 사항 확인은 문서·테스트 결재보다 동작하는 코드를 직접 써 보게 한다.
15. 추정 → 작업 기간·성능 추정에 단위와 불확실성을 붙이고, 추정을 기록해 맞춰 본다.

## 3장 기본 도구

16. 일반 텍스트의 힘 → 설정·데이터·로그는 사람이 읽을 수 있는 텍스트(JSON/YAML/CSV/Markdown) 우선.
17. 셸 가지고 놀기 → 반복 작업은 셸·스크립트로 자동화.
18. 파워 에디팅 → 에디터를 능숙하게. 
19. 버전 관리 → 모든 것을 버전 관리에. 작은 커밋, 의미 있는 메시지.
20. 디버깅 → 비난 말고 문제를 고친다. 재현부터, 가정은 검증, "그럴 리 없다"를 의심, 고무 오리에게 설명.
21. 텍스트 처리 → 텍스트 처리 언어(파이썬 등)로 코드 생성·변환을 자동화.
22. 엔지니어링 일지 → 결정·시도·결과를 기록한다.

## 4장 실용주의 편집증

23. 계약에 의한 설계 → 함수의 선행·후행 조건과 불변식을 밝힌다(타입 힌트, 검증, 독스트링).
24. 죽은 프로그램은 거짓말을 하지 않는다 → 이상하면 일찍 크게 실패. 예외를 삼키지 않는다.
25. 단정적 프로그래밍 → 일어날 수 없다고 생각하는 것은 assert로 확인.
26. 리소스 사용의 균형 → 연 것은 연 곳에서 닫는다(`with`, 컨텍스트 매니저).
27. 헤드라이트를 앞서가지 말라 → 피드백 받을 수 있는 작은 단계로. 먼 미래를 예측해 설계하지 않는다.

## 5장 구부러지거나 부러지거나

28. 결합도 줄이기 → 묻지 말고 시켜라, 데메테르 법칙(`a.b().c().d()` 체이닝 피하기), 전역 데이터 피하기.
29. 실세계를 갖고 저글링하기 → 이벤트·상태 기계·옵저버·스트림으로 반응형 구조.
30. 변환 프로그래밍 → 프로그램을 데이터 변환의 파이프라인으로 생각한다(입력 → 변환 → 출력).
31. 상속세 → 구현 상속 대신 인터페이스·프로토콜, 위임, 믹스인.
32. 설정 → 환경마다 다른 값은 외부 설정으로. 코드에 하드코딩하지 않는다.

## 6장 동시성

33. 시간적 결합 깨트리기 → 꼭 순서가 필요한 것만 순차로. 병렬 가능한 곳을 찾는다.
34. 공유 상태는 틀린 상태 → 공유 가변 상태를 피하고, 불가피하면 락·원자적 연산.
35. 액터와 프로세스 → 상태를 공유하지 않고 메시지로 소통.
36. 칠판 → 느슨한 협업은 공유 저장소(칠판) 패턴.

## 7장 코딩하는 동안

37. 파충류의 뇌에 귀 기울이기 → 코드가 이상하게 느껴지면 멈추고 이유를 찾는다.
38. 우연에 맡기는 프로그래밍 → 왜 동작하는지 알고 짠다. 문서화된 동작에만 기대고, 가정은 테스트로.
39. 알고리즘의 속도 → 빅오 감을 갖고, 측정으로 확인한다.
40. 리팩터링 → 일찍, 자주, 작게, 테스트와 함께. 기능 추가와 리팩터링을 섞지 않는다.
41. 테스트로 코딩하기 → 테스트는 첫 번째 사용자. 테스트하기 어렵다면 설계가 나쁜 신호.
42. 속성 기반 테스트 → 가정을 속성으로 표현해 자동 생성된 입력으로 검증(파이썬: hypothesis).
43. 바깥에서는 안전에 주의하라 → 입력을 믿지 않는다, 최소 권한, 비밀은 코드·저장소에 두지 않는다.
44. 이름 짓기 → 무엇을 하는지 드러나는 이름. 이름이 안 지어지면 설계를 다시 본다.

## 8장 프로젝트 전에

45. 요구 사항의 구렁텅이 → 요구는 수집이 아니라 대화로 파악한다. 사용자와 함께 확인.
46. 불가능한 퍼즐 풀기 → 진짜 제약인지 의심하고 틀 밖에서 본다.
47. 함께 일하기 → 페어·몹 프로그래밍.
48. 애자일의 핵심 → 작은 단계, 피드백, 조정의 반복.

## 9장 실용주의 프로젝트

49. 실용주의 팀 → 깨진 창문 없는 팀, 작고 안정적인 팀.
50. 코코넛만으로는 부족하다 → 형식(의식)만 따라 하지 말고 맥락에 맞는 것을 한다.
51. 실용주의 시작 도구 → 버전 관리·회귀 테스트·완전 자동화.
52. 사용자를 기쁘게 하라 → 코드가 아니라 사용자의 문제를 푼다.
53. 오만과 편견 → 자기 작업에 서명하고 책임진다.
