# 이력서 작성

사용자(소순원)의 경력 사실은 `~/code/doubles2/private/resume-data/profile.md`에 있다. **거기 없는 사실은 지어내지 않는다.**
없는 값이 필요하면 물어보고, 새로 받은 값은 profile.md에 반영한다.

이 폴더(`private/`)는 공개 repo에 올라가지 않는 비공개 repo `Doubles2/doubles2-private`이다.
폴더가 없으면 지어내지 말고 멈춘 뒤, `git clone https://github.com/Doubles2/doubles2-private ~/code/doubles2/private`를 안내한다.

작성 스타일은 `~/code/doubles2/private/resume-data/style.md`, 연봉 기재는 `~/code/doubles2/private/resume-data/salary.md`를 읽는다.
이 두 파일은 이력서 문장을 쓰기 전에 읽어야 한다. 나중에 고치면 전체를 다시 손봐야 한다.

## 도구

`~/code/doubles2/skills/resume/scripts/docxkit.py` 가 워드 편집을 담당한다. 매번 zipfile/ElementTree 보일러플레이트를
다시 쓰지 말 것. 한글 워드는 한 문장이 여러 run으로 쪼개져 있어서 단순 문자열 치환이
실패하는데, 이 스크립트는 단락 단위로 처리해 서식을 보존한다.

```bash
python3 ~/code/doubles2/skills/resume/scripts/docxkit.py dump    지원서.docx              # 표 좌표까지 구조 출력
python3 ~/code/doubles2/skills/resume/scripts/docxkit.py cell    지원서.docx 0 3 3 "줄1" "줄2"
python3 ~/code/doubles2/skills/resume/scripts/docxkit.py replace 지원서.docx "옛 문구" "새 문구"
python3 ~/code/doubles2/skills/resume/scripts/docxkit.py check   지원서.docx              # 제출 전 자동 점검
python3 ~/code/doubles2/skills/resume/scripts/docxkit.py pages   지원서.docx 지원서.pages  # Pages 변환
```

편집할 때마다 `.prev` 스냅샷이 자동으로 남는다. 여러 차례 고칠 것이므로 이게 있어야
사용자가 마음 놓고 되돌려달라고 할 수 있다.

## 워크플로우

### 1. 양식부터 이해한다
빈 원본 양식(`_지원자 이름_` 같은 파일)이 함께 있으면 **먼저 dump해서 대조한다.**
행 수, 열 구조, 안내 문구의 위치가 채워야 할 범위를 알려준다.
원본 없이 채운 지원서만 있으면, 사용자에게 원본이 있는지 물어보는 편이 빠르다.

### 2. JD를 분해한다
담당업무 / 지원자격 / 우대사항을 항목별로 쪼개고, 각 항목에 **profile.md의 어떤 경험이
대응하는지 표로 매핑한다.** 대응이 없는 항목은 갭으로 표시한다.
이 매핑이 이후 모든 문장 선택의 근거가 된다.

### 3. 사실 항목을 채운다
인적사항 · 학력 · 경력요약 · 자격 · 어학 · 교육 이수. 여기는 판단이 거의 없다.
다만 **날짜 정합성은 반드시 검산한다.** 생년월일과 학력 연도, 학력 졸업과 경력 시작이
이어지는지 본다. 사용자가 알려준 값이라도 어긋나면 계산해서 짚어준다
(예: 1990년생인데 고교 졸업이 2006.02면 중학교 졸업일 가능성이 높다).

### 4. 세부 경력을 서술한다
회사별로 `거버닝 메시지 → 프로젝트 블록 → 그 외 → 사용 역량` 순서.
프로젝트 선정은 JD 매핑표를 따른다. 같은 경력이라도 지원처마다 올릴 프로젝트가 다르다.

한 회사에 프로젝트가 몰려 있고 다른 회사가 `그 외 PoC:` 한 줄로 뭉쳐 있다면,
**JD 관련성이 높은 쪽을 본문으로 승격**한다. 분량 균형이 아니라 JD 기준으로 판단한다.

### 5. 용어를 정렬한다
JD가 쓰는 단어로 바꾼다. 같은 사실도 단어가 다르면 다른 경험으로 읽힌다.
- 카드사 지원 → `점포`를 `가맹 점포`로
- "데이터 상품 기획" JD → AWS 파이프라인을 기술 스택이 아니라 `데이터 상품화`로 서술
- "BI 사업" JD → 대시보드·리포팅에 `BI` 명시

단, 없는 경험에 단어만 씌우지 않는다. 갭은 갭으로 두고 사용자에게 알린다.

### 6. 점검하고 넘긴다
`docxkit.py check`를 돌린다. 자리표시자, 서술형 어미, 나열용 가운뎃점, 양식 지시문 잔존을
잡아준다. 빈 셀 목록은 의도적 공란인지 눈으로 확인한다.

제출 전 사용자에게 확인시킬 것:
- 회신 메일 3종 세트 (기존연봉 / 희망연봉 / 이직가능시기) — 공고가 본문 기재를 요구하는 경우가 많다
- 함께 제출할 서류 (개인정보 동의서 등)의 미기재 항목
- 면접에서 나올 질문 (경력 공백, 재입사, 도메인 갭)

## Pages(.pages) 파일을 받았을 때

Pages는 IWA(protobuf + snappy) 포맷이라 **직접 편집하면 서식 오프셋이 깨져 파일이 열리지 않는다.**
항상 `.docx`를 원본으로 두고 편집한 뒤 `docxkit.py pages`로 다시 내보낸다.

여러 번 고칠 예정이면 .docx만 수정해 두고 **마지막에 한 번만 Pages로 변환**한다.
변환할 때마다 Pages 앱이 실행되기 때문이다.

제출 파일은 `.docx`(또는 PDF)다. `.pages`는 편집용이지 제출물이 아니다.

## 동의서·서명란

개인정보 수집·이용 동의서 같은 서류는 성명·생년월일·날짜까지는 채워도 되지만,
**서명란은 사용자가 지시한 경우에만 채운다.** 동의 의사 표시라 대신 판단할 일이 아니다.
사용자가 요청하면 원본의 공백 길이를 유지해서 넣는다
(`지원자` + 공백 21칸 + `(서명)` → 이름 7자를 넣고 남은 14칸을 앞뒤 7칸씩).

## 파일 정리

작업이 끝나면 제출물만 최상위에 남기고 나머지(스냅샷, 빈 양식, .pages 중간본)는
`log/` 하위로 옮긴다. 무엇이 제출물인지 한눈에 보이는 상태로 넘기는 게 목적이다.

## 사용자를 대하는 방식

사용자는 문장을 직접 검토하고 자주 되묻는다. 판단이 들어간 곳은 **왜 그렇게 썼는지 근거를
함께 말한다.** "사업사 직무로 전환이 맞는 말이냐"처럼 되물어 오면, 방어하지 말고
정확히 무엇이 틀렸는지 (직무가 아니라 환경이 바뀐 것, `사업사`는 사내 약어) 짚고 대안을 준다.

지어낸 표현이 섞이면 사용자가 알아챈다. 확신이 없으면 물어보는 편이 빠르다.
